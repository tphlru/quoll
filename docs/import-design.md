## 1. Что такое импорт

Администратор загружает файл заказчика и переносит из него данные в систему. Два назначения:

- **Каталоги** — направления, вендоры и их контакты, продукты, программы, специальности, вузы, специальности вузов, контакты вузов. Файл актуализирует их: новое создаёт, существующее дополняет.
- **Реестр работы с вузами** — 10 полей ТЗ (вуз, вендор, ПО, номер договора, подписание лицензии, срок лицензии, статус передачи, ФИО менеджера, ответственные от вуза, комментарий) плюс колонки, которые мы добавили: программа, шаг, статус, «на шаге с», причина закрытия, поля шагов. Строка реестра — ветка (вуз × программа × продукт), все строки одного вуза — одна заявка.

Импорт ничего не удаляет: система не удаляет бизнес-данные (модель 10.1 п. 8). Заявку можно только закрыть.

## 2. Путь пользователя

1. **Формат.** Админ открывает раздел «Импорт». Видит описание формата: какие листы и колонки понимает система, какие обязательны, в каком виде писать даты, списки, статусы. Скачивает шаблон xlsx: лист на вид данных и лист «Инструкция».
2. **Загрузка.** Выбирает файл: xlsx, xls, csv или json, до 10 МБ, до 10 000 строк. Для реестра выбирает маршрут (по умолчанию — единственный опубликованный).
3. **Авторазбор.** Система сама определяет вид каждого листа (по имени, а у единственного листа — по заголовкам) и сопоставляет колонки с полями: точное совпадение, похожее название, распознавание по значениям (ИНН, email, телефон, даты). Всё неуверенное помечено. Колонки с лишними ПДн (паспорт, СНИЛС, дата рождения, адреса) вырезаются сразу и не сохраняются.
4. **Проверка сопоставления.** Админ видит, какая колонка куда легла, и может поправить: сменить вид листа, пропустить лист, переназначить колонку.
5. **Превью.** По каждой строке — статус:
   - **новая** — создаст запись;
   - **изменится** — какие поля, было → станет;
   - **без изменений**;
   - **конфликт** — нужно решение;
   - **ошибка** — не применится, пока не исправлена;
   - **исключена** — админ сам убрал её из импорта.

   И предупреждения, которые применению не мешают. Фильтры по листу, статусу, группе, «только с замечаниями».
6. **Правка.** Админ правит ячейки прямо в превью, выбирает запись из справочника вместо ненайденной, исключает строки. Каждая правка сразу пересчитывает превью.
7. **Конфликты.** Решает по группе или массово:
   - у вуза уже есть заявка → «пропустить, оставить прежнюю» или «заменить: прежняя закрывается, создаётся новая» (В7);
   - менеджер не найден или однофамильцы → выбрать менеджера или пропустить (В11).
8. **Файлы.** К строке реестра прикладывает файлы: договор, акт передачи и другие документы. После применения они становятся документами заявки.
9. **Применение.** Кнопка «Применить» доступна, когда нет нерешённых конфликтов. Применение идёт в фоне, экран показывает прогресс. Ошибка одной строки не останавливает остальные.
10. **Итог.** По каждой строке — применена, пропущена или не удалась и почему. Отчёт xlsx можно скачать. Повторная загрузка того же файла даёт «без изменений».
11. **Отмена.** Непримененную партию можно отменить: она и её файлы удаляются. Черновик живёт 24 часа с последней правки.

## 3. Правила каталогов

- **Ключи сопоставления** с тем, что уже есть (совпадают с уникальными индексами базы: `uq_products_name_vendor`, `uq_universities_inn_kpp`, уникальные названия вендора, направления, программы, код специальности):

  | Вид | Ключ |
  |---|---|
  | направление, вендор, программа | название |
  | продукт | название + вендор (в базе уникальна пара; одноимённые продукты у разных вендоров бывают). Вендор не указан — по одному названию, несколько совпадений — ошибка «укажите вендора» |
  | специальность | код ОКСО |
  | вуз | ИНН + КПП; КПП нет и вуз с таким ИНН один — он |
  | контакт | владелец (вуз или вендор) + ФИО |

- **Обновление:** непустое значение файла заменяет значение в базе, пустая ячейка ничего не стирает. Списки-связи (направления продукта, продукты программы, специальности вуза) только пополняются.
- **Повторы в одном файле:** строки с одним ключом, которые друг другу не противоречат, сливаются (пример: вендор на нескольких строках Вендоры.xlsx с разными контактами). Противоречие — ошибка на обеих строках.
- **Ссылки вперёд:** строка может ссылаться на запись, которую создаёт другая строка того же файла (программа на новое направление). Виды применяются по порядку: направления → вендоры → продукты → программы → специальности → вузы → специальности вузов → контакты → реестр.

## 4. Правила реестра

### 4.1 Заявка и ветки

- Группа строк одного вуза = одна заявка; поля уровня заявки (вуз, менеджер, номер и даты договора, статус) во всех строках группы должны совпадать среди непустых значений. Два разных номера договора у вуза — ошибка (модель §5).
- Программа обязательна; пусто — единственная программа продукта, иначе ошибка, исправляемая в превью (В10).
- Пара программа + продукт должна быть допустимой: продукт входит в программу, оба активны.

### 4.2 Где встаёт заявка

| Что в группе | Результат |
|---|---|
| есть номер договора или шаги веток | заявка подписана и стоит на шаге подписания; ветки — на своих шагах: явный шаг из файла, иначе «передано» → шаг 6, иначе шаг 5 (модель §5) |
| указан основной шаг, договора нет | заявка на этом шаге; ветки — черновики состава |
| ни договора, ни шага | заявка создаётся, назначается менеджеру и ждёт принятия (В2) |

- «Шаг» пишется названием или номером: «4» — это «4. Подписание», а не «4.1».
- Ветка на конечном шаге закрыта: «Ветка завершена» — без причины, «Ветка: отказ» — с обязательной причиной.
- Все ветки группы закрыты — заявка закрывается «все ветки закрыты, завершено» (В8).
- «на паузе» — ручная пауза заявки (В9).
- «Статус» из файла сверяется с тем, что получилось, расхождение — предупреждение.

### 4.3 Договор, лицензия, передача

- Номер и даты договора — документ «Договор». Файла может не быть: документ «Договор №…» без скана, скан потом подгружается новой версией (В1). Файл, приложенный в превью, главнее номера из ячейки.
- Лицензия: дата подписания и срок; «срок» 1–50 — годы, четырёхзначное число — год окончания (В4). «Лицензия до» считается системой.
- Договорные данные существующих записей не перезаписываются: расхождение — предупреждение (ответ 24). Договорные поля: номер договора, даты договора («подписан», «действует до»), лицензия (дата, срок), статус передачи, а также доп. поля продлений §4.8. Все они необязательные.

### 4.4 Менеджер

- ФИО полностью, «Фамилия Имя», «Фамилия И.О.» или email; регистр и «ё» не важны.
- Ищется среди менеджеров. Не найден или несколько — конфликт с выбором в превью (В11).
- Менеджер должен быть в строю (активен, без смены роли, принимает работу, есть руководитель) — иначе ошибка.
- Лимит заявок не проверяется, превышение — предупреждение «N из M» (В3).

### 4.5 «Ответственные от ВУЗа»

Ячейка делится на людей; из каждого вынимаются ФИО, телефон, email. Куда их положить, админ выбирает на группу (В12): в контакты вуза (по умолчанию), в контакты и ссылкой в поле шага типа «контакт», или не импортировать.

### 4.6 Время

- «На шаге с» — дата входа на шаг; застой считается от неё, если она относится к текущему шагу, иначе от момента импорта (В5). Будущие даты — ошибка.
- Дата договора — момент подписания заявки. Нет — момент импорта.

### 4.7 Сравнение с базой и конфликты

- Открытая заявка вуза совпадает по менеджеру, составу веток и шагам — «без изменений» (договорные расхождения — предупреждение).
- Отличается — конфликт: пропустить или заменить (В7: прежняя закрывается системной причиной «Заменена импортом», черновик отменяется).
- Открытой нет — новая заявка. Если группа закрывается (В8), она сравнивается с последней закрытой заявкой вуза из импорта, чтобы повтор файла дал «без изменений».

### 4.8 Доп. поля: состояния, которые иначе вносились бы вручную (В22)

Все необязательные. Без них импорт переносит только текущий шаг, дату входа на него, ручную паузу, подписание, лицензию, передачу и поля шагов.

| Колонка | Уровень | Что делает | Ограничения |
|---|---|---|---|
| «Пауза до» | заявка | пауза заявки до даты (как ручная пауза со сроком) | дата в будущем, иначе ошибка; вместе с «на паузе» — одна пауза |
| «Ветка на паузе» | ветка | бессрочная пауза ветки | ветка не закрыта |
| «Пауза ветки до» | ветка | пауза ветки до даты | дата в будущем |
| «Идёт допсоглашение», «Допсоглашение с» | заявка | открывает доп. прохождение шага «4.1 Допсоглашение» с пустым черновиком допсоглашения; дату входа — из «Допсоглашение с». Действия допсоглашения КАМ вносит сам | только подписанная заявка в работе; в маршруте есть доп. шаг допсоглашения |
| «Договор продлён до», «Дата продления договора» | заявка | «действует до» = новая дата; событие «договор продлён» (было → стало) датой продления | позже прежнего «действует до»; договорное поле (§4.3) |
| «Лицензия продлена до», «Дата продления лицензии» | ветка | «лицензия до» = новая дата; событие «лицензия продлена» датой продления | позже расчётного срока лицензии; договорное поле |

Данные пройденных шагов (дата встречи, дата запуска и т. п.) — колонками «<Шаг>: <поле>» для пройденного или текущего шага, как в ред. 2 §5.6.

## 5. Сквозные правила

- **Только администратор** (В6), включая реестр. Автор созданных заявок и событий — «система» с номером партии, кто запустил — в системном журнале (В13).
- **Лимиты — только для импорта:** xls, xlsx, csv, json; 10 МБ; 10 000 строк. Другие загрузки системы (документы) живут по своим правилам.
- **Превью не меняет рабочие данные**, применение перепроверяет каждую строку по текущей базе: что изменилось с превью и стало ошибкой или конфликтом — не применяется.
- **Строка (группа реестра) применяется целиком или не применяется**, ошибка одной не откатывает другие.
- **ПДн:** в партии хранятся зашифрованно, лишние колонки не сохраняются, в журнал и сообщения не попадают; файлы партии видит только админ; отменённая или истёкшая партия удаляется вместе с файлами.
- **Журнал:** применение партии, каждая импортированная заявка, отмена.
- **Повтор:** тот же файл после применения — «без изменений», в том числе для закрытых групп.

## 13. Жизненный цикл партии

### 13.1 Состояния

```
POST /imports ──> DRAFT ──PATCH… (пересчёт)──> DRAFT
                    │
                    ├── POST apply (CAS, version) ──> APPLYING ──worker: единица за единицей──> APPLIED
                    │                            ├── процесс упал: аренда истекла, другой worker продолжает с result IS NULL
                    │                            ├── единица падает N раз: FAILED IMP-191, дальше следующая (Т9)
                    │                            └── POST stop: оставшиеся SKIPPED IMP-193, партия APPLIED (§17.5)
                    └── POST cancel / истёк срок ──> удалена (с файлами)
APPLIED ──cancel / истёк срок──> удалена (документы заявок остаются)
```

### 13.2 Загрузка

```
POST /imports (admin, multipart file, workflow_id?)
    размер > import_max_size_mb → 413 IMP-008 (читаем потоком, обрываем на пределе)
    расширение ∉ {xlsx, xls, csv, json} → 415 IMP-002
    sheets = parsing.read(content, fmt)       # 422 IMP-001 нечитаемый, 422 IMP-009 строк > import_max_rows
    batch = ImportBatch(DRAFT, created_by=admin, filename, fmt, workflow_id=workflow_id или единственный опубликованный)
    для листа: mapping.detect(sheet) → kind, header_row, mapping, notes; ПДн-колонки вырезаны из raw
    вставить листы и строки (raw)
    analysis.run(session, batch)              # §16, пишет строки и summary
    журнал IMPORT_UPLOADED {batch_id, format, rows}  (без имени файла)
    201 BatchRead
```

Файл целиком в S3 не кладётся: после разбора он не нужен, всё нужное — в строках партии.

### 13.3 Срок жизни

- DRAFT: `expires_at = updated_at + import_draft_ttl_hours`, любая правка продлевает.
- APPLIED: `expires_at = applied_at + import_applied_ttl_days` — итог можно смотреть и скачивать неделю.
- APPLYING не истекает, но и не застревает: M16.

### 13.4 Удаление партии (`service.drop`) — общее у отмены и очистки

```
batch = lock_row(ImportBatch) (отмена) | SELECT … FOR UPDATE SKIP LOCKED (очистка)
под блокировкой: отмена — status ∈ {DRAFT, APPLIED} иначе 409 IMP-010; очистка — expires_at < now() и status != APPLYING
ids  = attachment_id из import_files партии, где attachment_id IS NOT NULL
keys = storage_key этих attachments
DELETE import_batches WHERE id = batch.id          # каскад: листы, строки, import_files
DELETE attachments WHERE id ∈ ids                   # к документам заявок они не привязаны (M7): применённые уже без attachment_id
журнал IMPORT_CANCELLED {batch_id} — только отмена
commit; затем s3.delete(key) для keys: сбой логируется, запись уже удалена (как document_service.delete_document)
```

Очистка — `Periodic("import-cleanup", import_cleanup_interval_seconds)`, каждая партия — своя транзакция.

## 15. Разбор файла

### 15.1 Чтение (`parsing.py`)

| Формат | Как |
|---|---|
| xlsx | `openpyxl.load_workbook(read_only=True, data_only=True)`, все листы |
| xls | `xlrd.open_workbook(file_contents=…)`, все листы; даты — `xldate_as_datetime(value, book.datemode)` по типу ячейки |
| csv | кодировка `utf-8-sig`, затем `cp1251`; разделитель — `csv.Sniffer(delimiters=";,\t")`; один лист с именем файла без расширения |
| json | массив объектов — один лист; объект `{лист: массив}` — листы; заголовки — ключи в порядке первого появления; вложенное значение — `json.dumps` |

- **Лимит строк** считается по ходу чтения: как только непустых строк данных суммарно больше `import_max_rows`, чтение обрывается — 422 IMP-009 (защита от раздутых книг). Реестр отдельно: `import_max_registry_rows` проверяется после выбора вида, ERROR на листе `IMP-104`, применение запрещено.
- **Ячейка → строка:** `None` → ""; дата/время → ISO-дата; float с целым значением → без «.0»; bool → «да»/«нет»; иначе `str().strip()`.
- **Строка заголовков** — первая из первых 10, где непустых ячеек ≥ `min(2, число колонок)`. Выше — пропускаются, пустые строки данных тоже. Номер строки — файловый, с 1.
- **ПДн-колонки** (§14.1) вырезаются из `raw` при разборе; заголовок остаётся в `headers` с пометкой `personal_data`.
- Любое исключение библиотеки чтения → 422 IMP-001 без текста исключения (errors-ru §3 п. 6).

### 15.2 Вид листа и колонки (`mapping.py`)

**Нормализация заголовка:** нижний регистр, «ё» → «е», убрать «*», всё в скобках, кавычки, повторные пробелы, знаки по краям.

**Вид листа:**
- Книга с несколькими листами — только по имени (`sheet_synonyms`). Не совпало — лист пропущен (`kind = NULL`, замечание листа `IMP-101` «выберите вид»). Так пропускаются «Заметки» и «Инфраструктура (не продукты)».
- Единственный лист: по имени; иначе по заголовкам — вид, у которого найдены все обязательные поля и не меньше двух полей, с наибольшим числом найденных; ничья или никто — `kind = NULL`.

**Колонки:**
1. точное совпадение с синонимом;
2. `difflib.SequenceMatcher(None, a, b).ratio() ≥ 0.85` с лучшим синонимом → note `fuzzy`;
3. по значениям: колонка без поля, ≥ 80% непустых значений проходят образец ещё не занятого поля вида (inn — 10 цифр и сумма; kpp — 9 цифр; email; phone — ≥ 10 цифр; okso; url; date) → note `by_values`;
4. ПДн-заголовок → `personal_data`, сопоставить нельзя (422 IMP-012 при правке);
5. два заголовка на одно поле → левый, у правого `duplicate`;
6. остальное → `unused`.

Правка (`PATCH …/sheets/{n}`) пересобирает строки листа из `raw` и пересчитывает партию.

### 15.3 Нормализация значений (`normalize.py`)

- **Ключ названия:** casefold, «ё» → «е», убрать кавычки «»„“"', схлопнуть пробелы, убрать точку в конце. «ООО», «ПАО» не убираются: это часть названия.
- **Списки:** разделители из `list_sep`; запятая режет только вне кавычек; элемент — strip и снятие внешних кавычек.
- **ИНН/КПП:** цифры; проверка ИНН — `_inn` переносится из `catalog/schemas.py` в `core/validators.py` и используется обеими сторонами.
- **Телефон:** цифры; 11 цифр с 8 или 7 в начале → `+7…`; 10 → `+7…`; иначе как есть и warning `IMP-120`.
- **Email:** нижний регистр, `^[^@\s]+@[^@\s]+\.[^@\s]+$`, иначе ERROR `IMP-110`.
- **Регион:** точное совпадение с `REGIONS` после нормализации; иначе `ratio ≥ 0.9` → warning `IMP-123` с подставленным регионом; иначе ERROR `IMP-110`.
- **Дата:** ISO; `дд.мм.гггг`; `дд.мм.гг` (век 20); `дд/мм/гггг`; число — excel-серия (только csv и json, где тип не сохранился). Иное — ERROR `IMP-110`.
- **enum и bool** — по `enum_values` после нормализации.

## 16. Анализ (`analysis.py`, `registry.py`)

### 16.1 Ход

```
run(session, batch):
    snap = Snapshot.load(session, batch)              # §16.2, фиксированное число запросов на вид
    pending = {}                                       # (kind, part, key) -> row_id первой строки
    для листа по KINDS[kind].order, строки по number:
        values, labels, issues = разобрать raw по mapping, наложить edits
        по частям вида: найти запись по ключу, pending, diff, предусловия (16.11)
        status: EXCLUDED | ERROR | NEW (есть NEW-часть) | UPDATE (есть diff) | SAME
    registry.run(snap, строки реестра)                # §16.6-16.10: группы, шаг, конфликты
    для строки: digest = sha256(status, issues, targets, group_key, data.values, data.diff)
        записать только строки с изменившимся digest (16.12)
    batch.summary, batch.version += 1
```

Полный пересчёт при каждой правке; строки в памяти; рабочие таблицы не меняются (M1).

### 16.2 Снимок

`Snapshot.load` — по запросу на справочник, только нужное:
- направления, вендоры, продукты (вендор, направления, `is_active`), программы (продукты, `is_active`), специальности, вузы (`id, inn, kpp, short_name, full_name`), пары вуз — специальность;
- менеджеры — `User` + `Manager`: ФИО, email, роль, `is_active`, `identity_sync_status`, `role_transition_status`, `manual_workload_status`, `superviser_id`, `max_active_projects` и загрузка (`manager_load_subquery`);
- маршрут партии: стадии (с `is_terminal`, `is_side`, `is_branch_stage`, `is_branch_start`, `archived_at`, `fields`, `stall_days`, `passive_after_days`, `parent_stage_id`), активные рёбра (`edge_facts`), опорные стадии §16.7;
- для вузов реестра: открытая заявка с ветками и шагами; последняя закрытая с событием `IMPORT`;
- причины закрытия, виды документов;
- контакты — лениво по владельцу (ПДн не ищутся SQL-ом), с кешем.

### 16.3 Ключи и сопоставление

- Направление, вендор, программа — нормализованное название; специальность — код.
- **Вуз** (лист вузов): КПП есть — точная пара; нет — одна запись с ИНН → она, несколько → ERROR `IMP-111` «укажите КПП».
- **Ссылка на вуз** из других видов по порядку: 10 цифр с верной суммой → по ИНН (несколько — ERROR `IMP-111`); точное нормализованное краткое название; полное. Несколько — ERROR `IMP-111`. Не найден, но есть NEW-строка вузов партии с тем же ИНН или названием — ссылка `{"new_of_row": id}`. Нет — ERROR `IMP-006`.
- **Продукт:** с вендором — пара; без — по названию, несколько → ERROR `IMP-111` «укажите вендора».
- **Контакт:** загружаются контакты владельца, сравнение в Python по нормализованному ФИО.
- **Правка-ссылка** `{"id": …}` берётся как есть после проверки, что запись существует и подходит по виду.

### 16.4 Части строки и diff

- Нашлась запись → `diff` по непустым полям файла, которые отличаются от базы. Пусто в файле — поле не сравнивается (M4). Списки-связи: в diff только добавляемые элементы.
- Договорные поля (`contract`) существующих записей в diff не попадают: расхождение — warning `IMP-130` (M4, ответ 24).
- Не нашлась → NEW; обязательные поля из `spec` + прогон `*Write`-схемы каталога на значениях части (длины, образцы, регион): `ValidationError` → ERROR `IMP-110` с полем.
- UPDATE → `diff` прогоняется `*Patch`-схемой (`catalog_service.update` с dict её не прогоняет): `ValidationError` → ERROR `IMP-110`. Применение передаёт в `update` значения, уже прошедшие схему.

### 16.5 Повторы ключа и ссылки вперёд

- `pending[(kind, part, key)]` — первая строка с этим ключом, чья часть NEW или UPDATE без ошибок.
- Повтор той же части: значения не противоречат (совпадают или дополняют пустые) → часть сливается в первую строку, у повтора info `IMP-140` `{ref_row}`; противоречат → ERROR `IMP-141` `{ref_row}` на обеих.
- Ссылка на запись, которую создаёт строка более раннего вида партии, — `{"new_of_row": id}` без ошибки. Строка-источник не применилась — ссылающаяся при перепроверке FAILED `IMP-142`.

### 16.6 Реестр: группы и сведение

- Группа — строки с одним вузом: `group_key = u:<id>` или `r:<row_id>` для NEW-вуза партии. Исключённые строки в группу не входят.
- Группа применяется целиком: хоть одна строка группы ERROR — все её строки ERROR, у остальных `IMP-189` `{ref_row}` «ошибка в строке группы». Так применение не путает её с «изменилось с превью».
- Поля `group` среди непустых значений совпадают, иначе ERROR `IMP-150` `{ref_row}` на расходящихся. Пустое берёт значение группы. `contacts` объединяются.
- Программа пуста: единственная программа, куда входит продукт, иначе ERROR `IMP-151` (В10).
- Пара программа — продукт: программа активна; продукт активен и входит в программу, иначе ERROR `IMP-152` «добавьте продукт в программу» (В15, повторяет `contract_service.check_pair`).
- **В14:** вендор не найден → NEW-часть «вендор» строки (warning `IMP-153`); продукт не найден (с вендором) → NEW-часть «продукт» с направлением программы строки (warning `IMP-153`). Такой продукт в программу не добавляется — значит пара нарушает В15 → ERROR `IMP-152` с подсказкой. Поэтому на деле реестр создаёт вендора и продукт, когда связь с программой задана листом программ той же партии.
- Две одинаковые пары (программа, продукт) в группе — ERROR `IMP-154` (живая ветка пары одна, `draft_branch`).

### 16.7 Шаг и статус группы

**Опорные стадии маршрута** (считаются в снимке):
- `S0` — начальная (ребро из NULL);
- `SEAL` — основная не-доп. стадия, из которой идёт необратимое ребро в `B0` (в эталоне «4. Подписание»); несколько — с минимальной `position`;
- `NR` — точка невозврата маршрута без веток: цель необратимого ребра основных стадий (`move_locked` на таком ребре зовёт `open_branches`, а та ставит `no_return_at`); несколько — с минимальной `position`; нет необратимого ребра — нет и точки невозврата;
- `B0` — `is_branch_start`;
- `B1` — единственная нетерминальная стадия веток, куда ведёт прямое ребро из `B0` («6. Внедрение»); нет или несколько — нет;
- `DONE` — терминальная основная стадия с прямым ребром из `SEAL` («Завершено»); нет или несколько — нет;
- `AGR` — доп. стадия (`is_side`) с обработчиком `SUPPLEMENTARY_AGREEMENT`, вход из `SEAL`.

**Разбор «Шаг»** (нормализовано, только неархивные): точное имя; номер `N` или `N.M` — стадия, имя которой начинается с этого номера и затем `.` + не цифра, пробел или конец («4» → «4. Подписание», не «4.1»); два кандидата — ERROR `IMP-111`; доп. стадия — ERROR `IMP-155` (допсоглашение — колонкой «Идёт допсоглашение»).

**Таблица для группы.** `contract` = номер договора есть; `bs` — шаги строк, являющиеся стадиями веток; `ms` — основные шаги строк.

| # | Условие | Результат |
|---|---|---|
| 1 | `ms` и `bs` непусты одновременно | ERROR `IMP-156` на всех строках |
| 2 | в `ms` больше одной стадии | ERROR `IMP-157` |
| 3 | `ms` = {терминальная} | ERROR `IMP-158` «закрывайте ветки» |
| 4 | `contract` или `bs`, маршрут без веток (нет `B0`) | заявка на `ms` или `S0`; ветки — черновики APPROVED; `signed_at` = момент подписания; `no_return_at` — только если есть `NR` и шаг заявки — `NR` или после него (`leads_to(прямые рёбра, NR, шаг)`), как при ручном проходе через необратимое ребро; иначе `NULL` |
| 5 | `contract` или `bs`, есть `SEAL` и `B0` | подписана; заявка на `SEAL`; `ms` ∉ {∅, {SEAL}} → ERROR `IMP-159`. Шаг ветки: её `stage` из `bs`; иначе TRANSFERRED → `B1` (нет `B1` → ERROR `IMP-160`), иначе `B0`. Явный `B0` при TRANSFERRED → warning `IMP-161` |
| 6 | нет договора, `bs` пусто, `ms` = {S} | заявка на S; ветки — черновики: APPROVED, если S = SEAL, иначе PROPOSED |
| 7 | нет договора, шагов нет | В2: без шага, назначена, ждёт принятия; без менеджера — черновик, warning `IMP-162` |

- **Закрытая ветка в файле** — два способа, как в ручном процессе:
  - **завершена:** `stage` — терминальная стадия веток, в которую ведёт активное ребро из нетерминальной стадии веток («Ветка завершена»); причина не нужна; итог DONE (как ручной переход по ребру, `branch_service._place`);
  - **отказ:** непустая «Причина закрытия» уровня BRANCH; ветка встаёт на свой рабочий шаг (явный `stage` из `bs` или по умолчанию) и закрывается событием `CLOSE` с причиной (как `branch_service.close_locked`). `stage` — терминальная стадия без входящего ребра («Ветка: отказ») принимается как синоним «отказ на шаге по умолчанию», warning `IMP-163`; без причины — ERROR `IMP-163`.
  - Причина при нетерминальном шаге без слов «отказ» — всё равно отказ на этом шаге.
- **В8:** все ветки группы на конечных шагах → заявка закрывается (§19.5); нет `DONE` → ERROR `IMP-164`.
- **Статус** не хранится, сверяется: «подписан» без подписания, «в работе» при подписании, «завершено»/«отказ» без закрытия — warning `IMP-165`; «на паузе» → ручная пауза заявки (В9); для строки 7 — ERROR `IMP-166`.

### 16.9 Менеджер

- **Форматы:** «Фамилия Имя Отчество», «Фамилия Имя», «Фамилия И.О.», «Фамилия И. О.», «Фамилия И.», email. Иное — ERROR `IMP-003`.
- **Поиск** без учёта регистра и «ё» среди пользователей с ролью «менеджер»; человек с другой ролью — ERROR `IMP-167`.
- Не найден / несколько — **CONFLICT** `IMP-004` / `IMP-005`, в `params` — кандидаты `[{id, name}]` (ФИО сотрудников — не ПДн вуза, модель §9). Снимается выбором (`manager_choice` любой строки группы → на всю группу) или SKIP (В11).
- **В строю:** `is_active`, `identity_sync_status = OK`, `role_transition_status = NONE`, `manual_workload_status = AVAILABLE`, есть руководитель (G8) — иначе ERROR `IMP-168` (повторяет `assert_can_take_new_work` и `assign_locked`). Проверяется у групп NEW и REPLACE; у SAME менеджер только сравнивается с владельцем.
- **Выбор в превью:** `GET /imports/{id}/managers?q=` — менеджеры с ФИО, руководителем и готовностью (`effective_status_expression`); общий список пользователей для этого не годится (только админский, без фильтра роли и поиска). Нужен и группе строки 7 без менеджера, и при пустом списке кандидатов.
- Пусто: строки 4–6 — ERROR `IMP-169`; строка 7 — warning `IMP-162`.
- **Лимит (В3):** моделируется: занято по снимку + группы партии по порядку, которые займут слот (строки 4–6, не закрытые, без паузы) → warning `IMP-175` `{used, max}`.

### 16.10 Сравнение с базой

- **(а)** открытая заявка вуза; **(б)** иначе, если группа закрывается (В8), — последняя закрытая заявка вуза с событием `IMPORT`.
- **Сравниваются** — то, что импорт сам ставит, в том же виде:
  - владелец (выбранный в превью менеджер тоже сравнивается);
  - строки файла ↔ ветки заявки: пара (программа, продукт) строки ищется среди веток последней итерации пары, **включая закрытые**; нет — различие состава;
  - шаг заявки; шаг ветки; закрытость ветки и её вид (завершена / отказ с причиной);
  - закрытость заявки;
  - доп. поля: пауза заявки и ветки, активное доп. прохождение `AGR`, продления — совпадает с состоянием или нет.
- Договорные поля и доп. поля-продления — не конфликт, а warning `IMP-130` при расхождении.

| Итог | Статус строк группы | Решение |
|---|---|---|
| (а) или (б) совпадает | SAME | — |
| (а) есть и отличается | CONFLICT: `IMP-180` владелец, `IMP-181` состав, `IMP-182` шаг | SKIP — SKIPPED; REPLACE — §19.6 |
| (а) нет, (б) не совпадает или нет | NEW | — |

- Решение ставится на группу; `POST …/decisions` — массово.
- Конфликт группы — набор причин: с базой (`IMP-180…182`) снимает SKIP или REPLACE; менеджера (`IMP-004/005`) — выбор или SKIP. Группа не CONFLICT, когда сняты все.
- **REPLACE привязан к заявке (M17).** При решении в строку пишется `replace_target = {interaction_id, fingerprint}`; отпечаток — `sha256` от `state_id`, `owner_id`, `closed_at`, `no_return_at`, `pause_state` и отсортированных `(branch_id, state_id, closed_at)` веток. Анализ при каждом пересчёте сверяет: открытая заявка вуза — другая или отпечаток изменился → решение снимается, группа снова CONFLICT с `IMP-186` «заявка изменилась после решения». Перепроверка в применении (§17.3) делает то же под блокировкой: не совпало → FAILED `IMP-190`, ничего не закрыто.
- REPLACE над заявкой со шагом требует стадию закрытия для её маршрута: `batch.replace_stages = {workflow_id: stage_id}` (терминальная основная стадия этого маршрута); нет для маршрута группы — CONFLICT остаётся с `IMP-187`, `apply` 409 IMP-011. Над черновиком стадия не нужна.
- Уровень причины при REPLACE — по `close_reasons.interaction_level(old)` (по `no_return_at`, как `check_reason`), не по «подписана»: `INTERACTION_AFTER_SIGNING` → `REPLACED_BY_IMPORT_AFTER`, иначе `_BEFORE`.
- У SKIP- и SAME-групп файлы, контакты и комментарии не применяются — warning `IMP-183`.

### 16.12 Производительность

Цель: пересчёт партии на 10 000 строк при правке — ≤ 2 с на стенде (нефункц. 1 касается экрана, здесь — отзывчивость превью). Средства: одна расшифровка/шифрование на строку (Т1); снимок фиксированным числом запросов; запись только строк с изменившимся `digest`. Тест §26 п. 12 меряет; превышение — повод для инкрементального пересчёта по листу, не для ослабления порога.

## 17. Применение

### 17.1 Запуск

```
POST /imports/{id}/apply {version}
    batch = lock_row(ImportBatch); status == DRAFT иначе 409 IMP-010
    batch.version != version → 409 IMP-018 «превью устарело, обновите» (M17: админ видел не это)
    changed = analysis.run(batch)                     # свежий пересчёт; changed - изменился ли digest хоть одной строки
    changed → session.commit() (пересчёт, снятые решения и новая version сохраняются), затем 409 IMP-018 {version: новая}
              - иначе get_db_session откатил бы пересчёт, и фронт снова увидел бы старое превью
    есть CONFLICT без снятия → 409 IMP-011 {groups: [group_key]}
    есть ошибка листа (IMP-104, IMP-017) → 409 IMP-019 {sheets}
    status = APPLYING; apply_started_at = now; lease_until = NULL; worker_id = NULL; next_attempt_at = NULL
    summary.progress = {done: 0, total: единиц к применению}
    журнал IMPORT_APPLIED не здесь - в конце (§17.3)
    commit; 202 BatchRead
```

Пересчёт внутри `apply` нужен: база могла измениться с последнего превью. Если он что-то меняет — админ не видел итог: пересчёт фиксируется, `apply` отказывает (IMP-018) с новой `version`, фронт перечитывает партию и показывает новое; следующий `apply` с этой версией проходит, если база снова не изменилась. `analysis.run` не меняет `version`, если ни один `digest` не изменился — иначе `apply` отказывал бы всегда.

### 17.2 Взятие (`worker.claim`)

```
Periodic("import-apply", import_worker_interval_seconds):
    одна транзакция:
        batch = SELECT … WHERE status = 'APPLYING'
                  AND (lease_until IS NULL OR lease_until < now())
                  AND (next_attempt_at IS NULL OR next_attempt_at <= now())
                ORDER BY id FOR UPDATE SKIP LOCKED LIMIT 1
        нет → выход
        lease_version += 1; worker_id = host:pid; lease_until = now() + IMPORT_LEASE_SECONDS
    commit
    Keycloak (Т7): verify_target для каждого менеджера групп без итога, по одному разу;
        после каждого менеджера - короткая транзакция продления:
            UPDATE import_batches SET lease_until = now() + IMPORT_LEASE_SECONDS
            WHERE id = … AND lease_version = version AND status = 'APPLYING'
            0 строк → аренду перехватили или партию остановили - выход (M11)
        IdentityProviderUnavailable →
            idp_retries < IMPORT_IDP_RETRIES: отложить (CAS: lease и worker - NULL,
                next_attempt_at = now + min(30 с × 2^idp_retries, 30 мин), idp_retries += 1), выйти
            иначе: продолжить без проверки - группы, чья проверка не удалась, FAILED IMP-194 «Keycloak недоступен»
        учётка отключена или роль не та → группы этого менеджера FAILED IMP-168 в свою очередь
    run(batch_id, version, недоступные менеджеры)
```

Один процесс берёт одну партию за такт; единицы идут последовательно — порядок видов важен.

### 17.3 Единица (`worker.run_unit`)

Единица — строка каталога или группа реестра, по порядку видов (`order`), внутри — по номеру (у группы — номер первой строки). Берутся только строки с `result IS NULL` (M12).

```
для единицы:
    async with session_maker() as db:
        try:
            async with db.begin():
                batch = lock_row(ImportBatch)                          # уровень 0, до всего остального
                batch.status != APPLYING или batch.lease_version != version → стоп исполнителя (M11)
                batch.lease_until = now() + IMPORT_LEASE_SECONDS
                все строки единицы EXCLUDED / ERROR / SKIP / SAME → result = SKIPPED (код причины); done += n; continue
                savepoint:
                    перепроверка единицы по текущей базе под блокировками → ERROR, CONFLICT без снятия,
                        не совпал отпечаток REPLACE → FAILED IMP-190 (M3, M17)
                    применить: §18 (каталог) | §19 (реестр)
                    result = APPLIED, result_ids
                AppException → rollback savepoint; FAILED, result_code = код исключения или IMP-191
                IntegrityError/DBAPIError → rollback savepoint; FAILED IMP-192
                done += n
            # commit: изменения и итог - одной транзакцией (M12)
        except ИсполнительОстановлен: выход
        except любое другое исключение (баг, обрыв соединения):
            лог с трассой; отдельная транзакция: lock_row(ImportBatch), CAS lease_version и status = APPLYING:
                attempts первой строки единицы += 1
                attempts >= IMPORT_UNIT_ATTEMPTS → строки единицы FAILED IMP-191, done += n; следующая единица
                иначе → аренда отпускается (lease и worker - NULL), next_attempt_at = now() + 30 с;
                        выход исполнителя: та же единица повторится на следующем взятии (порядок видов сохраняется)
            не удалось и это (база недоступна) → выход; аренда истечёт, такт повторит
после всех единиц: finish(batch_id, version, stopped=False)
```

**`finish(batch_id, version, stopped)`** — общее завершение исполнителя и остановки (§17.5), одна транзакция:
```
batch = lock_row(ImportBatch); status == APPLYING иначе выход
не stopped: CAS lease_version == version иначе выход; остались строки с result IS NULL → выход (такт продолжит)
stopped: lease_version += 1 (ограждает исполнителя, M11); строки с result IS NULL → SKIPPED IMP-193
status = APPLIED; applied_at = now(); expires_at = applied_at + import_applied_ttl_days
lease_until, worker_id, next_attempt_at - NULL
summary: итоги по видам и результатам - запросом по import_rows, не из памяти исполнителя
уведомления §19.10 - тоже запросом по import_rows
журнал IMPORT_STOPPED | IMPORT_APPLIED {batch_id, счётчики}, actor_id = кто остановил | batch.created_by
```
Исход не зависит от того, кто успел: второй вызов под блокировкой видит APPLIED и выходит.

- Savepoint внутри транзакции единицы: откат изменений строки не откатывает блокировку партии и запись итога.
- Исключение вне savepoint (например, обрыв соединения) откатывает всю транзакцию — итога нет; попытка засчитывается отдельной транзакцией; если и она не прошла (база недоступна), аренда истечёт и следующий такт повторит. Предел попыток не даёт одной единице держать партию (M16).
- Процесс упал — аренда истекает через `IMPORT_LEASE_SECONDS`, другой такт продолжает с первой единицы без итога.
- Снимок вида перечитывается перед каждым видом: предыдущие уже в базе, `new_of_row` разрешаются в id по `result_ids` строк-источников.
- `result_ids` группы реестра — `{interaction_id, manager_id, closed, replaced_interaction_id?, branch_ids, document_ids}`.

### 17.4 Блокировки единицы реестра

Порядок `core/locking.py`, уровень `ImportBatch` ставится первым (до `Superviser`), и в docstring это дописывается:
1. `lock_row(ImportBatch)`.
2. `share_stage` на все стадии, куда встанут заявка и ветки группы, `AGR`, `DONE` и стадию закрытия заменяемой — по возрастанию id (стадии раньше заявки — как у ходов веток).
3. REPLACE: `lock_interaction_scope(прежняя, None, target_manager_ids=[новый])` — берёт `Manager` (прежний владелец, новый), `User` (они, руководитель прежнего, автор) и заявку в порядке уровней. Если владелец сменился между чтением и захватом, `lock_interaction_scope` откатывает свой savepoint — блокировки, взятые после savepoint, Postgres отпускает, — и повторяет; три неудачи — `InteractionChangedConcurrentlyException` → FAILED IMP-192. Предварительного захвата строк до области нет: он и был источником нарушения порядка (ред. 3, п. 3).
4. `create_interaction`, затем `lock_interaction_scope(новая, None, [новый])`: `Manager[новый]` и `User[новый]` уже взяты в п. 3 (или берутся здесь впервые, без REPLACE); новая заявка не видна другим транзакциям — ждать некого.

Руководитель нового менеджера не блокируется: `assign_locked` его не читает, G8 проверяется по `Manager.superviser_id` заблокированной строки менеджера.

### 17.5 Остановка применения

`POST /imports/{id}/stop` (админ): `status == APPLYING` иначе 409 IMP-010; `finish(batch_id, None, stopped=True)` (§17.3) — ждёт блокировку, то есть текущую единицу; строки без итога — SKIPPED `IMP-193`; уведомления по уже применённым группам уходят. Исполнитель на следующей единице или в своём `finish` видит другой `lease_version` или APPLIED и выходит (M11). Нужна, когда админ не хочет ждать отложенного Keycloak или ошибся с партией (M16).

- **UPDATE** — `catalog_service.update(session, model, target, id, changes: dict, None)`; `changes` — из `diff`; списки-связи — объединение текущих id и новых.
- **Специальности вуза** — `INSERT … ON CONFLICT DO NOTHING` в `university_specialties`; журнал `CATALOG_ITEM_UPDATED` вуза `{specialties_added: [...]}`.
- **Контакты** — `create` / `update` с `ContactWrite` / dict; в журнал — только перечень полей (`catalog_service._journal_value`).
- Автор записей журнала каталога — «система»; кто запустил — в `IMPORT_APPLIED`.

## 19. Применение: реестр (`place.py`)

### 19.1 Событие `IMPORT`

Постановка на шаг из файла пишется записью истории `kind = IMPORT`, `transition_id = NULL`, `actor_id = NULL`, `payload = {"batch_id": …}`, `created_at` — дата из файла. Для заявки — `transition_service.place(..., kind=IMPORT, ...)` (§19.3); `place()` начинает возвращать созданную запись истории, чтобы вызывающий выставил `created_at`. Для ветки — запись в `seal_imported` (§19.4).

**Даты и порядок (M18).** Лента — история заявки (без ветки и доп. прохождения) или история одной ветки.
- Первое событие ленты — её `IMPORT`: у заявки — дата входа на шаг (у подписанной — дата договора), у ветки — `max(«на шаге с» ветки, дата договора)`.
- Остальные датированные события ленты — не раньше её `IMPORT`, вставляются в порядке дат:
  - лента ветки: продление лицензии — более ранняя дата сдвигается к `IMPORT` ветки, warning `IMP-188`;
  - лента заявки: продление договора — дата не раньше подписания требуется анализом (IMP-173), так что сдвиг не нужен;
  - доп. прохождение — своя лента (`side_pointer_id`): `SIDE_STARTED`, `SA_OPENED` с датой «Допсоглашение с», не раньше подписания (IMP-172).
- Момент подписания без даты договора — `earliest` группы (§19.2), а не момент импорта: иначе любые прошлые даты допсоглашения и продления договора были бы «раньше подписания».
- События без даты из файла (пауза, закрытие по В8, комментарии) — моментом импорта, последними.
- Так `id` и `created_at` в ленте упорядочены одинаково, и отчёт за любую прошлую дату видит согласованное состояние.

**Пройденные шаги (В27).** Перед основным `IMPORT` ленты пишутся отметки «пройден» — `kind = IMPORT`, `from_stage_id = to_stage_id = x`, `payload = {batch_id, passed: true}`, та же дата, что у основного `IMPORT` ленты:
- `x` — нетерминальные не-доп. стадии ленты, для которых `leads_to(прямые рёбра, начало, x)` и `leads_to(прямые рёбра, x, текущий)`, `x ≠ текущий`; «прямые» — активные, не `is_backward` (`edge_facts`); начало — `S0` для заявки, `B0` для ветки; порядок вставки — по `position`;
- для них работает всё, что опирается на «шаг был в истории»: правка значений (`step_service.set_values` — `visited`), откат ветки (`branch_service.rollback`), откат и переоткрытие заявки (`reached_since_no_return`);
- в отчётах не видны: у отметки шаг не меняется (`from = to`), `_move` такие не берёт, а статус определяется последним событием — основным `IMPORT`;
- у подписанной группы основной `IMPORT → SEAL` несёт `payload.sealed = true`, и `transition_service.reached_since_no_return` считает такое событие точкой невозврата наравне с переходом по необратимому ребру (§19.11): отметки стадий до `SEAL` не открывают откат подписанной заявки за точку невозврата — как после ручного подписания.

`earliest` (В25) — самая ранняя дата группы из файла: «на шаге с» строк и группы, дата договора, «Допсоглашение с»; нет ни одной — момент импорта. Её получают назначение (`reports/policy.interaction_allowed` требует его раньше конца периода) и `created_at` веток (`row_kinds` отбрасывает ветки, созданные после конца периода). Даты событий не раньше `earliest` по построению.

Порядок важен: договор до допсоглашения (вход в `AGR` проверяет документ договора); закрытия и пауза — последними (пауза закрытой невозможна, В8 и пауза взаимоисключены анализом).

### 19.4 `contract_service.seal_imported(session, scope, rows, signed_at)`

```
signed = полночь BUSINESS_TZ даты договора; нет даты - earliest группы (§19.2); нет и её - now()
interaction.signed_at = interaction.no_return_at = signed
для строки группы:
    branch = черновик пары (создан create_interaction); contract_status = APPROVED
    step = шаг ветки строки (§16.7; для отказа - рабочий шаг)
    at = max(since ветки, signed)
    branch.state_id = step; branch.opened_at = at; branch.stall_since = since ветки или now()
    license_signed_at, license_term_years (В4), transfer_status; bindings._derive_license(branch)
    отметки «пройден» ветки: стадии от B0 до step (§19.1, В27), дата at
    h = история IMPORT (branch_id, from NULL, to step, payload {batch_id}); h.created_at = at
    [продление лицензии - §19.7: событие после h, дата max(license_extended_at, at)]
    last = дата последнего события ленты ветки (h или продления)
    «завершена» (step терминальная): branch.closed_at = at; unpause_branch; close_reason_id = NULL
    «отказ»: branch_service.close_locked(scope, branch, close_reason_id=…, comment=f"import #…",
             offer=False, closed_at=last) → branch.closed_at и created_at события CLOSE = last
журнал BRANCHES_OPENED {branches}
```

- `opened_at = at`, а не момент импорта: отчёт видит ветку на шагах с даты её шага, а до неё — как ветку состава со статусом заявки «на подписании» (IR15 отчётов). Путь ветки до известного шага в файле не описан — это приближение, а не выдумка шагов.
- `since` ветки раньше подписания — событие датируется подписанием, warning `IMP-177`.
- Строка 4 (маршрут без веток): `signed_at`; `no_return_at` — по правилу §16.7 (есть `NR` и шаг заявки не раньше него); ветки APPROVED. Точка невозврата в истории — событие стадии `NR` (основной `IMPORT` или отметка «пройден») с `payload.sealed = true`: отметки до неё не открывают откат за неё (В27).
- `close_locked` ветки после закрытия зовёт `_offer_to_close` — уведомление руководителю «все ветки закрыты»; для импорта оно не нужно: `branch_service.close_locked` получает `offer: bool = True`, импорт передаёт `False`.
- Лента ветки пишется целиком внутри `seal_imported` в порядке: отметки, `IMPORT`, продление лицензии, закрытие — `id` и даты идут одинаково (M18). Пауза отказной или завершённой ветки невозможна: §16.8 требует открытую ветку (IMP-171). Пауза открытой ветки — моментом импорта, после её ленты (§19.2).
- История заявки: `place_imported(SEAL, since = signed)` — заявка «на подписании с» даты договора.

### 19.5 Допсоглашение (`side_pointer_service.start_locked`)

`start` делится на `start_locked(session, scope, entry, comment)` — всё после захвата области — и обёртку. Импорт:

Право `can_change` в `start_locked` не проверяется — оно в обёртке (права у импорта — админ, В6).

### 19.7 Договор (В1)

- Номер: у файла CONTRACT группы есть — он; иначе из строки; разные — warning `IMP-178`, побеждает файл.
- Есть файл → документ CONTRACT с файлом и реквизитами; нет файла, есть номер → документ CONTRACT без файла, `title = «Договор №<номер>»`; ни того ни другого — документа нет.
- Стадия документа — SEAL (строка 4 — шаг заявки); `status = ACTIVE`; `uploaded_by = NULL`; журнал `DOCUMENT_ATTACHED` (actor NULL).
- Продление: `contract.contract_valid_until = contract_extended_until`; история `CONTRACT_EXTENDED` `payload {old, new, document_id, batch_id}`, `created_at = max(contract_extended_at, IMPORT заявки)` (M18); журнал `CONTRACT_EXTENDED`. Формат `payload` — как у `sa_service` (без `sa_id`): `bindings.extension_locks` после этого запрещает правку срока полем шага, как после допсоглашения.
- Лицензия: после `_derive_license` при `license_extended_until` — `branch.license_until = новая`, история `LICENSE_EXTENDED` `payload {old, new, batch_id}`, `created_at = max(license_extended_at, IMPORT ветки)` (M18). Отчёт берёт «лицензию до» на прошлую дату из `old` (`reports/policy.license_at`).

### 19.8 Файлы строк → документы

- Стадия по умолчанию: CONTRACT, CONTRACT_DRAFT → SEAL (строка 4 — шаг заявки; 6/7 — шаг заявки, если есть, иначе ERROR `IMP-179` в анализе); вид из `required_document_kinds` ребра, выходящего из шага ветки строки или предшествующих ему → этот шаг; иначе шаг ветки (подписанная) или заявки.

### 19.9 Контакты группы (В12)

- `CATALOG` — каталог вуза (§18); `STEP:<stage_id>:<key>` — каталог и ссылка в поле шага: `step_contacts.resolve(session, stage, university_id, {key: {…}}, None)` возвращает id и ничего не пишет в значения шага — id входит в общий словарь значений стадии, который пишется одним `_upsert` (§19.2); лишние люди — только в каталог (warning `IMP-185`); `SKIP` — не импортировать.
- Варианты `STEP:*` — поля типа `contact` шагов уровня заявки, пройденных или текущих для группы.

### 19.10 Уведомления (В16)

- `assign_locked(..., announce=False)` не шлёт `INTERACTION_ASSIGNED` (параметр по умолчанию `True`).
- В финальной транзакции партии счётчики — запросом по `import_rows` партии: группы с `result = APPLIED`, у которых `result_ids.manager_id` задан и `result_ids.closed` ложно, сгруппированные по менеджеру; закрытые по В8 не считаются (работы нет). Так счёт верен и после перехвата аренды.
- Два вида: `IMPORT_ASSIGNED` (INFO, роль `USER`, «Импортом назначены заявки», «Вам назначено заявок: {count}») — менеджеру; `IMPORT_ASSIGNED_TEAM` (INFO, `USER`, «Импортом назначены заявки», «{manager}: назначено заявок {count}») — его руководителю. `emit(..., subject=SYSTEM, actor_id=None, audience=Audience(users=(id,)))`.
- Сторож (застой, истекающие лицензии и договоры, пассивные) — как обычно. Бездействие импортированной заявки считается от импорта (В28): `slot_changed_at = now()` входит в `slots.last_activity`, поэтому пассивной она станет не раньше `passive_after_days` после импорта, одинаково для всех групп. Истории смены слота это не пишет: слот при импорте не меняется, он изначально активный.

### 19.11 Актор «система»: что меняется в сервисах

`lock_interaction_scope(actor_id=None)` уже возвращает `actor = None`. Функции, которые импорт зовёт с такой областью и которые сейчас читают `scope.actor.id`, получают `actor_id = scope.actor.id if scope.actor else None`, а проверки прав — через флаг:

| Функция | Изменение |
|---|---|
| `project_service.assign_locked` | `actor_id` из области; `by_import` уже есть; новые `announce: bool = True` и `assigned_at: datetime | None = None` (передаётся в `_hand_over`, В25) |
| `project_service._hand_over` | `assigned_at` — дата открываемой записи назначения; `None` — момент транзакции, как сейчас |
| `project_service.pause` | выделить `pause_locked(session, scope, stage, until, comment)`; права и стадия — в обёртке (`_pausable`); актор из области |
| `project_service.cancel_draft` | выделить `cancel_draft_locked(session, scope, close_reason_id, comment, allow_system=False)` |
| `transition_service.place` | возвращает запись истории |
| `transition_service.reached_since_no_return` | точка невозврата — ещё и событие заявки `kind = IMPORT` с `payload.sealed = true` (В27); `max(id)` из обоих видов |
| `transition_service.close_locked` | `by_import: bool = False` — без `can_close`, `allow_system=True` в обе `check_reason`; актор из области |
| `branch_service.pause` | выделить `pause_locked(session, scope, branch, until, comment)`; актор из области |
| `branch_service.close_locked` | актор из области; `offer: bool = True` (импорт — `False`); `closed_at: datetime | None = None` — момент закрытия ветки и `created_at` события `CLOSE` (импорт, §19.4); `None` — `now()`, как сейчас |
| `side_pointer_service.start` | выделить `start_locked` §19.5 |
| `close_reasons.check_reason` | уже принимает `allow_system` |

Остальные функции импорт не зовёт. Прав админа импорт не проверяет на каждом шаге: право — у ручек `/imports` (В6).

   - `entered` уже считает `IMPORT` из NULL принятием.

13. `docs/import-format.md` — генерируется `template.py`.

## 23. Гонки и сбои

| Ситуация | Что происходит | Почему безопасно |
|---|---|---|
| Две правки одной партии | последовательны под `lock_row(ImportBatch)`, выигрывает последняя; `version` растёт | M8 |
| Правка во время применения | ждёт транзакцию единицы, видит APPLYING → 409 IMP-010 | M8 |
| Два `apply` | второй под блокировкой видит APPLYING → 409 | M8 |

| Исполнитель уснул, аренду перехватили | его следующая транзакция единицы видит чужой `lease_version` и останавливается; текущая, если уже в работе, держит `lock_row(ImportBatch)` — перехватчик ждёт её коммита, и она успевает только свою единицу с итогом | M11, M12 |
| Процесс упал посреди единицы | транзакция откатилась, итога нет → единица повторится у следующего | M12 |

## 25. Краевые случаи

1. Лист без строк данных — `counts = 0`, не ошибка.
2. Строка, где все сопоставленные ячейки пусты, — пропускается при чтении.
3. Одна и та же группа на двух листах реестра — один `group_key`, сводится как одна группа.
4. Два листа одного вида — строки сводятся по ключам как один набор.
5. Смена маршрута партии — правки `step:*` и сопоставления `step:*` снимаются (I на листе).
6. Стадия из файла в архиве — ERROR IMP-111 (не найдена среди живых).
7. Вуз в реестре есть только как NEW на листе вузов, а его строка — ERROR — группа FAILED IMP-142.
8. «Срок лицензии» «2031» при подписании 2026 → 5 лет; без даты подписания — ERROR IMP-176.
9. `pause_until` через 40 дней — ERROR IMP-170 (720 ч), как у ручной паузы.
10. Допсоглашение у группы, закрываемой по В8, — ERROR IMP-172.
11. REPLACE заявки на другом маршруте — нужна `replace_stages[её маршрут]`; нет — CONFLICT IMP-187 только у этой группы.
12. Менеджер стал недоступен между превью и применением — FAILED IMP-190 (перепроверка) или IMP-168.
13. Файл к исключённой строке — 409 IMP-020.
14. Удаление документа без файла руками — удаляется строка документа, S3 не трогается.
15. Скан к договору без файла — новая версия с `replaces_document_id`, реквизиты наследуются.

## 26. Тесты

Файлы данных строятся в тесте (openpyxl, csv, json); для xls — фикстура. Применение — прямой вызов `worker.claim` + `run` с `session_maker` (как сторож и очередь отчётов).

1. **Разбор:** xlsx с титульной строкой и «*»; xls с датой; csv cp1251 «;»; json с листами и вложенным значением; лимит строк (IMP-009); нечитаемый (IMP-001 без текста); 413/415.
2. **Сопоставление:** по имени листа в книге (служебные пропущены); по заголовкам у одного листа; fuzzy; по значениям; ПДн вырезаны и не сопоставляются (IMP-012); unused.
3. **Каталоги:** seed → NEW; применение; повтор SAME (M5); пустое не стирает (M4); слияние и противоречие (И2); ссылка на новую запись партии; продукт одного имени у двух вендоров; специальности вуза пополняются.
